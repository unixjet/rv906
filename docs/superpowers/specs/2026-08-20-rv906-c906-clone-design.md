# RV906: A Textbook-Grade Verilog Clone of the XuanTie C906 — Design

Date: 2026-08-20
Status: Draft for review

## 1. Purpose and Positioning

RV906 is a **complete, readable, hand-written Verilog re-implementation of the
T-Head XuanTie C906** processor, built as a *textbook-grade* reference —
directly analogous to the RV12 project (`../rv12`), which clones C910. The
original openc906 RTL (`refs/openc906/C906_RTL_FACTORY/gen_rtl/`, ~139K lines)
is machine-generated: many small ctrl/dp file pairs, non-obvious cross-unit
signal names, terse structure. It is authoritative but not teaching material.
RV906 reproduces the same microarchitecture in the coding style of the
RVProc6 project — few files, clear pipeline stages, explicit stall/flush
feedback — so a reader can study how a real, shipped, single-issue in-order
RISC-V core actually works.

Where C910 is an out-of-order superscalar cluster, C906 is a 5-stage,
single-issue, in-order core: the microarchitecture is simpler, but every
subsystem is still a real, silicon-proven design (non-blocking D-cache with
hardware stream prefetch, a Gshared branch predictor, a standard RISC-V Debug
implementation) — richer subject matter than a from-scratch teaching core,
without the scale of an OoO machine.

The project has two phases:

1. **Phase 1 (this project)**: hand-written Verilog clone, fully verified
   (riscv-tests, Linux boot, cross-check against the original C906 RTL), and
   — unlike RV12 — carried through to **FPGA bring-up** (§7.4, §11).
2. **Phase 2 (a later project)**: re-implementation in C2RTL C++, in the
   manner of RVProc6, using the verified Verilog as its blueprint.

All code and documentation are written in **English only**.

## 2. Scope

### 2.1 What is cloned

The clone boundary is the single-core `openc906` level (this release of
openc906 is single-core; there is no cluster/coherence fabric to clone):

- **5-stage, single-issue, in-order pipeline**: IFU, IDU, EU (IU + FPU), LSU,
  RTU (§5).
- **IU**: ALU (single-cycle, forwarding-covered), MULT (16×16/32×32/64×64),
  DIV (iterative, variable latency), BJU (branch resolution in EU).
- **Scalar FPU**: FALU / FMAU / FDSU (radix-4 SRT divide/sqrt), half/single/
  double precision, configurable as a whole.
- **L1 caches**: I-Cache 32KB/2-way, D-Cache 32KB/4-way, 64B line, Harvard.
  D-Cache is non-blocking (dedicated miss buffer) with hardware stream
  prefetch into L1; I-Cache does critical-instruction-first refill on miss.
- **MMU**: Sv39, hardware page-table walk plus C906's extended
  software-refill mode; 128-entry jTLB.
- **PMP**: 8 entries (this build's configuration), 4KB granularity.
- **AXI4.0 128-bit master** interface, critical-word-first, configurable
  CPU:AXI clock ratio.
- **CLINT + PLIC** (this build wires 240 interrupt sources).
- **RISC-V Debug, version 0.13.2**: DTM + DM + SBA-over-AXI (`tdt/`), and the
  core-side trigger/breakpoint module (`dtu/`: `mcontrol` CSR, PC trace FIFO).
- **The stall/forward hazard network**: a chained, point-to-point
  backpressure discipline, not a global broadcast stall bus — see the
  alignment contract below.

Alignment contract: **microarchitecture is aligned to C906** — stage names
and count, cache geometry and associativity, predictor structures, the
hazard/stall signal topology, instruction behavior. Structure sizes and
signal topology are extracted from the original RTL when each subsystem is
specified in detail (never quoted from memory). In particular, the hazard
network must be cloned as C906 actually builds it: every stall signal is
either **confined to the unit that produces it** or **crosses exactly one
unit boundary as a named, single-purpose handshake** (e.g. `idu_ifu_id_stall`
between IDU and IFU) — never referenced directly by more than its one
immediate neighbor. This is a deliberate correction of the alternative
pattern (a handful of raw stall bits read directly by every pipeline stage),
which is simpler to write but does not scale in fanout as more hazard
sources are added; see `docs/superpowers/specs/` discussion notes for the
concrete comparison that motivated this rule.
**File organization and coding style are NOT aligned** — they follow the
RVProc6 conventions in §6.

### 2.2 What is not cloned

- **The vector unit (VPU)**: openc906's vector extension uses pre-ratification
  **RVV 0.7.1-draft** mnemonics (e.g. `vext.x.v`, `vfredsum.vs` without the
  "u"), not the ratified RVV 1.0 ISA, and needs T-Head's own toolchain fork
  for anything beyond scalar XThead extensions. Vector opcodes trap as
  illegal instructions, matching a C906 configuration with the vector unit
  disabled.
- **Multi-core / coherence fabric**: not applicable — this openc906 release
  is single-core (confirmed from `mp_top_golden_port.v` / `aq_sysio_top.v`
  port and signal naming: no snoop/coherence wiring).
- **Configurability**: openc906's own configuration surface (FPU
  precision subset, cache sizes, jTLB/PMP entry counts, debug resource
  level, interrupt count — manual Table 1.1) is **not** parameterized in
  Phase 1. RV906 hardcodes this build's actual configuration. Making these
  knobs configurable (in the spirit of RVProc6's `CONFIG_*` macros, though
  not necessarily using the same mechanism) is deferred to a future version,
  after the fixed-configuration clone is fully implemented and verified —
  see §11.
- **On-chip CLINT/PLIC RTL**: replaced by the proven rocketM RTL versions
  (`CLINT.v`, `PLIC.v`), as RV12 does.
- **Physical-design collateral**: hard SRAM macros become one behavioral
  `SRAM.v`; clock-gating cells become register enables; `rst`/`clk` top
  modules and pad wrappers are dropped.

### 2.3 Configuration parameters

Phase 1 has none — see §2.2. The only "parameter" is which milestone is
active; there is no `NUM_CORES`/`HAS_L2`-style knob because there is nothing
to vary. A future configurability pass would introduce a parameter table
here.

## 4. Top-Level Architecture

```
RVProcAXI.v (SoC wrapper; the only DUT the testbench sees)
├── RVProc.v                <-> openc906 core   single core, no cluster/CIU
│   ├── IFU.v ICache.v BPU.v                     fetch pipeline + Gshared
│   │   │                                        predictor + L1I (2-way)
│   ├── IDU.v                                    decode + hazard/dependency
│   │   │                                        check, single-issue dispatch
│   ├── IU.v FPU.v                                EU: ALU/MULT/DIV/BJU +
│   │   │                                        FALU/FMAU/FDSU (scalar F/D)
│   ├── LSU.v DCache.v                            LD/ST, non-blocking L1D
│   │   │                                        (4-way) + miss buffer + HW
│   │   │                                        stream prefetch
│   ├── MMU.v          <-> mmu/                  jTLB, PTW, sv39
│   ├── PMP.v          <-> pmp/                   physical memory protection
│   ├── CSR.v          <-> cp0/                   privilege, CSRs, interrupts
│   └── (DTU.v when HAS_DEBUG core-side hooks)    trigger/breakpoint, mcontrol
├── CLINT.v PLIC.v                                from rocketM
├── AXICrossbar.v AXIWidthAdapter.v ...           from rocketM
└── (TDM.v / TDT.v: JTAG DTM+DM+SBA)               RISC-V Debug 0.13.2
```

One external AXI4.0 master port. Memory and peripherals (ExtMem, UART, ...)
live in the C++ testbench during Phase 1 (§7.1); FPGA bring-up (§7.4/M9)
additionally targets RVProc6's existing board support (`board/`) as the
integration reference, since C906's own interface (AXI4.0, configurable
CPU:AXI clock ratio) is exactly what that support was built for.

## 5. Pipeline Panorama

Stage names follow C906's own unit names (IFU/IDU/EU/LSU/RTU), taken from the
manual's block diagram (§2.1) and RTL directory names (`ifu/`, `idu/`, `iu/`,
`lsu/`, `rtu/`).

### 5.1 The five stages

| Stage | Subsystem | Function |
|---|---|---|
| IFU | fetch | up to 2 instructions/cycle; Gshared branch predictor; I$ access (tag+data, 2-way); critical-instruction-first refill on miss; prefetch/instruction buffer decouples fetch from decode |
| IDU | decode | strictly single-instruction decode; data-dependency/hazard check against in-flight instructions; dispatch to EU |
| EU | execute | IU (ALU/MULT/DIV/BJU) and FPU (FALU/FMAU/FDSU) in parallel; branch resolved same stage |
| LSU | memory | load/store address + data, byte/half/word/double/quad with sign/zero extension, internal store→load forwarding, non-blocking D$ (4-way) access via a dedicated miss buffer, hardware stream prefetch into L1D |
| RTU | retire | architectural commit; precise exceptions/interrupts become visible here |

Note the fetch/decode width asymmetry: the front end fetches 2 instructions
per cycle into the buffer, but IDU decodes and the machine executes strictly
one instruction at a time (`单发`/single-issue) — this is *not* a superscalar
core, the wide fetch only exists to keep the buffer full past taken branches
and cache-line boundaries.

Predictor structure sizes (RAS depth, BTB entries, whether the BHT numbers in
the manual's Table 1.1 — "16Kb" — correspond to a single Gshared table or a
family of tables) are **not asserted here**; they are extracted from the RTL
during the M1 sub-spec, following the same discipline as RV12 (§9 of that
design).

### 5.2 The hazard/stall network

C906 handles hazards with the classic **stall + forward** in-order interlock
(no scoreboard, no OoO issue): forwarding paths in IU and LSU eliminate the
common cases (the manual states explicitly that single-cycle ALU ops and
store-data reuse have zero stall latency because of forwarding); a stall is
only needed where forwarding cannot cover the latency — multi-cycle
MULT/DIV/FDSU, load-use, D$/I$ miss, and retire-triggered flush.

The RTL confirms the stall signals are **topologically local**: signals like
`idu_frontend_stall`, `idu_backend_stall`, `ctrl_ex1_stall`,
`ctrl_dis_dep_stall` are referenced only inside the unit that defines them;
`idu_ifu_id_stall` crosses exactly the IDU↔IFU boundary and nowhere else.
RV906 must clone this topology, not the alternative (a handful of raw stall
bits consulted directly by every stage) — see the alignment-contract note in
§2.1.

### 5.3 Memory subsystem

LSU's internal forwarding covers store-to-load hazards; the D$ miss buffer
tracks outstanding misses so the LSU can support hit-under-miss rather than
blocking the whole pipeline on every miss; the hardware stream prefetcher
issues ahead-of-demand fetches into L1D. MMU provides a joint (128-entry)
TLB with an Sv39 hardware page-table walker, plus C906's extended
software-refill mode for cases the hardware walker doesn't cover.

## 6. Coding Conventions

The "rocketM recipe", identical to RV12's: Verilog-2001 plus a strict, small
SystemVerilog whitelist. Every file follows the same grammar.

### 6.1 Language whitelist

1. `typedef struct packed` — **only** for pipeline-register bundles and entry
   types **inside** a module; never on ports.
2. One `rvproc_pkg.sv` — parameters, opcodes, shared functions; files
   `import` it.
3. `logic` as a type where convenient.

Everything else is Verilog-2001: `always @*` and `always @(posedge clk or
negedge rst_n)` (no `always_comb`/`always_ff`), flat `input wire`/
`output wire` ports, `generate`, `function`, `localparam`, memory arrays. No
`interface`, `modport`, `enum`, classes.

### 6.2 Structural rules

1. **Top file is the table of contents**: `RVProc.v` instantiates IFU → IDU →
   EU → LSU → RTU in pipeline order, with a feedback/stall-and-flush section
   first — the whole core legible in one screen.
2. **One struct per pipeline boundary**, named after the two stages it joins
   (`if_id_t`, `id_ex_t`, `ex_lsu_t`, `lsu_rtu_t`). The struct documents what
   the stage passes on.
3. **One section per stage**; combinational first, sequential last; **each
   pipeline register has exactly one writer**
   (`if (flush) ... else if (!stall) ...`).
4. **Feedback section** at the top of every file lists every signal flowing
   against the pipeline (`stall_*`, `flush_*`) with its source.
5. **Each pipeline boundary exposes exactly one combined stall/ready signal
   to its immediate upstream neighbor.** Raw hazard-detection bits are never
   read by a non-adjacent stage; a stage that needs to know "can I advance"
   folds every local reason (its own hazard checks, plus its immediate
   downstream neighbor's one stall signal) into its own single outgoing
   signal. This is the rule that keeps the network's fanout bounded as
   subsystems are added — see §5.2.
6. **Entry arrays, never per-entry modules**, for anything repeated (TLB
   entries, PMP entries, miss-buffer entries).
7. **A submodule earns its own file** only if it has independent state +
   a clean interface (BPU, ICache, DCache, MMU, MULT, DIV, FDSU). Pure logic
   stays in the subsystem file. Target ≤ ~2–3K lines per file.
8. **Cross-module buses** are flat concatenated vectors with widths in
   `rvproc_pkg.sv` and accessor functions — no magic slicing at use sites.

### 6.3 Uniform physical conventions

- SRAMs: one behavioral `SRAM.v` (sync read).
- No clock gating cells; register enables express the same intent.
- Reset: asynchronous active-low `rst_n`.
- Naming: `<stage>_<meaning>` signals; struct types `<stage>_<stage>_t`. A
  signal glossary in `docs/01-conventions.md` maps RV906 names to original
  C906 names.
- Every file header states which original files it covers (traceability).

## 7. Verification

### 7.1 Framework (reused, rocketM/RVProc6 wiring)

```
rv906/
├── testbench/            reused from RVProc6/RV12: TestBench, load_elf, build_fdt
├── RVProcTest.cpp        C++ AXI slaves (ExtMem, UART) + address decode;
│                         CLINT/PLIC are RTL
├── dut.h dut.cpp         Verilator model wrapper, clock loop
├── verilator.mk scripts/ build flow, from rocketM
└── test/                 bare-metal tests: hello/clint/plic/intr
```

### 7.2 Observability

Unlike C910, C906 is **in-order**: architectural register state is directly
visible at retire (no PRF/rename-map reconstruction needed).

- **Commit trace** at retire: `{pc, insn, rd, wdata}` written to a trace
  file — the primary debugging index.
- **Spike diff**: the same ELF runs on Spike; scripts diff the commit
  sequences offline. First divergent instruction → cycle → waveform.
- Verilator FST waveforms on demand.

### 7.3 Toolchain

`/opt/xpack-riscv-none-elf-gcc-15.2.0-1`. GCC 15.2 has upstream support for
XThead scalar extensions, so smart_run-derived and custom-extension tests
can mostly be built without T-Head's proprietary toolchain; any smart_run
case that genuinely needs it is confined to the milestone that exercises it.

### 7.4 Milestones

Each milestone is an independent spec → plan → implementation sub-project,
aligned to the original from the start (no throwaway simplified versions).

| # | Content | Pass criteria |
|---|---|---|
| M0 | scaffold: build flow + testbench + AXI/CLINT/PLIC ported from rocketM/RV12 | full-chain Verilator build; AXI ExtMem smoke test |
| M1 | front end: IFU + ICache + Gshared predictor | directed fetch/prediction tests |
| M2 | integer machine end-to-end: IDU + IU + RTU + LSU base path + DCache + minimal CSR | rv64ui/um pass |
| M3 | full LSU: non-blocking D$, miss buffer, hardware stream prefetch, atomics | rv64ua pass + directed hit-under-miss tests |
| M4 | privilege complete + MMU (jTLB, PTW, sv39) + PMP + counter CSRs | rv64si/mi + vm tests pass |
| M5 | scalar FPU (F/D, half-precision transfers) | rv64uf/ud pass |
| M6 | interrupt path (CLINT/PLIC/CSR) integration | bare-metal interrupt tests; **single-hart Linux boot** |
| M7 | RISC-V standard Debug (JTAG DTM + DM + SBA, core-side `dtu` hooks) | debug register/halt-resume/breakpoint test cases |
| M8 | cross-check vs original openc906 RTL: same smart_run (non-vector) binaries on both simulators | functional parity; cycle-count comparison noted, not gated |
| M9 | **FPGA bring-up** (target board TBD; RVProc6's `board/` support is the integration reference) | boots on real hardware; runs the M2–M6 bare-metal test kit on-chip |

### 7.5 Path to FPGA (M9)

This is a deliberate divergence from RV12, which excludes FPGA bring-up as a
non-goal. C906 is a realistic FPGA target (a real single-issue in-order
core, AXI4.0 with a configurable CPU:AXI clock ratio built for exactly this),
and RVProc6 already has working board support to reference. M9 is scoped
after M0–M8 are green in simulation; the open points in §9 (board choice,
how much of RVProc6's AXI4-Lite board glue can be reused vs. needs adapting
to C906's full AXI4.0 master) are resolved in the M9 sub-spec, not here.

## 9. Risks and Open Points

- **Predictor structure sizes**: the manual's Table 1.1 "BHT 16Kb" entry is
  not yet resolved to concrete table depth/index-bit counts; extracted from
  RTL in the M1 sub-spec (never quoted from memory, matching RV12's own
  rule).
- **Stall-topology cloning discipline**: §5.2/§6.2 rule 5 is easy to state
  and easy to violate under time pressure (it is simpler to read one more
  raw signal from a distant stage than to thread a new local handshake).
  Each subsystem's spec should call out its stall signals explicitly so
  review can check the rule holds.
- **jTLB/PMP exact structure**: 128-entry jTLB and 8-entry PMP are pinned by
  the manual's Table 1.1 for this build's configuration; internal
  organization (set-associative vs fully-associative, replacement policy)
  is extracted from `mmu/rtl/` and `pmp/rtl/` during the M4 sub-spec.
- **FPGA target board**: not chosen yet; RVProc6's existing `board/nexysa7`
  support is the default reference, but C906's native AXI4.0 (full) vs.
  RVProc6's AXI4-Lite board glue may need an adapter. Resolved in the M9
  sub-spec, not blocking M0–M8.
- **smart_run compatibility**: vector cases are excluded (out of scope);
  non-vector cases needing the T-Head toolchain are confined to M8.
- **Cycle-level fidelity is not a goal**: parity is functional/structural.

## 10. Non-Goals

- The vector unit (VPU): non-standard RVV 0.7.1-draft, out of scope.
- Multi-core / coherence: not applicable to this openc906 release.
- Configurability across openc906's own configuration surface (deferred to
  a future version — §2.2, §2.3).
- Cycle-exact equivalence with the original RTL.
- Physical design collateral (clock gating cells, hard SRAM macros, DFT).

Unlike RV12, **FPGA bring-up is explicitly in scope** (M9, §7.4–7.5) — this
project is expected to run on real hardware, not just in simulation.
