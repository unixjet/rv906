## 1. D-M8-5 and the m6-wfi calibration (T2 follow-on)

T2 re-pointed the `time` CSR (0xC01) read from the CLINT-mtime mirror to
`mcycle_reg` (per-cycle). Documented deviation from the donor, which
reads the SoC mtime (`refs/openc906/.../aq_hpcp_top.v:2655`): rv906 has no
mtime mirror register at the CP0, and the only test-visible consumer
(m6-wfi) is calibrated against the mtime MMIO instead.

Consequence exercised by the T10 battery: the pre-T2 m6-wfi read t0 from
`time` (now per-cycle) and scheduled mtimecmp ~1000 mtime-ticks in the
future — it FAILs on the T2 tree BY DESIGN (that is the documented
deviation biting a test, not an RTL regression). m6-wfi now reads/writes
the CLINT mtime MMIO (0x0200BFF8) for both t0 and the wake-time check,
and its wake-time assertion is the RANGE `[t0+2, t0+4]` rather than exact
`t0+2`: the handler's own mtime read lands ~90–110 cycles after the mtip
fires (wake + retire + flush + icache cold miss of the never-fetched
handler + prologue + the MMIO load), straddling the very next 100-cycle
tick. Pass-through-wfi detection is intact (low bound + `mepc ==
post_wfi`). m6 suite: 8/8.

## 2. coremark cycle-count build sensitivity (documented, NOT gated)

The T2 one-line change (`csr_read_mux` 0xC01 arm: mtime mirror →
`mcycle_reg`) shifted coremark's final cycle count 503729 → 503406 with
NO other functional change. Root-caused and bounded by bisection
(controller-run, two fresh worktree builds per state):

| build state                          | final_cycles | verdict |
|---                                    |---|---|
| 27f1718 (T4d-11+14, pre-T2)          | 503729 | PASS (×2 independent builds) |
| 27f1718 + the single T2 line         | 503406 | PASS |
| 198d9f1 (= 27f1718 + T2)             | 503406 | PASS (×2) |

Evidence:
- Same coremark.elf (md5-identical, never rebuilt between states).
- The 24 CSR instructions in coremark never address 0xC01 (15 fflags,
  2 mstatus, 2 mcause, 1 mtvec, 1 each of 0x7c5/0x7c2/0x7c1/0x7c0).
- The parity trio (csr 345 / interrupt 512 / MMU 730) is BIT-EXACT
  across both builds — the shift is coremark-specific, not a global
  pipeline change.
- Generated-Verilator-C++ diff between the two builds: only the intended
  0xC01 mux arm plus statement reordering in three other files
  (Verilator's scheduling moves `u_clint.mtime`-adjacent statements and a
  memctl block; no semantic change).

Mechanism: `csr_addr = idu_cp0_ex1_src1_data[11:0]` (CSR.v:473) selects
the read-mux arm from the LIVE EX1 src1 operand bits on non-CSR cycles,
so the 0xC01 arm's value is sampled into `csr_rdata` on random cycles;
all downstream consumers are correctly gated (`is_csr_op`/`csr_wen`/
`wb_vld`), so the value is dead — but Verilator's constant/structure
propagation re-schedules surrounding combinational logic differently in
the two builds, and the re-scheduling lands differently on coremark's
~500k-cycle path. Classification: build-structure sensitivity of the
simulator's generated code, not an RTL behavioral difference; the
PASS/FAIL gate is stable across both states. Per D-M8-6, cycle counts
are annotated, never gated — this anomaly does not affect the parity
verdict (donor 435894.5 is annotated on the same footing).
